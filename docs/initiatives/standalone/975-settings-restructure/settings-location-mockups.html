  • Button actions stay under Node Settings. Buzzer and tones move beside Notifications, which Message Settings already advertises in its subtitle.
  • Split apart, each half needs its own capability gate: a buzzer-only radio must show tones and hide button actions.
  • Gates: Button actions on caps byte 2 0x02, Buzzer and tones on 0x01. Firmware already sets the two independently, and the screen already shows each half from its own bit; what changes is the entry and where it lives.

Why these choices, so a later change knows what it is breaking

One three-way control, not a toggle plus a picker

The badge's own screen does exactly this: setGpsMode() at MyMesh.h:458 writes both fields, and gpsEnabledForMode exists for the writer that sets both. What is forbidden is a bool-only writer clobbering the mode byte. An earlier draft had two controls and was wrong; #969's original wording pointed that way.

One status row, not two

Activity and last fix were separate blocks in the first draft. In a dense app that is one job taking two slots, so they are merged into a single ListTile between the selector and the coordinates.

Sleep interval is not the reporting interval

gps_interval is a reporting cadence; gps_ps_interval_s is a power duty cycle (NodePrefs.h:73-78). They live in different cards so the difference is visible, and are never merged.

Deferred, tracked separately

GPS fix state in the Channels and Contacts headers is #974; it lands in the same shared app-bar widget as epic #613, so it must follow #614 rather than run beside it. Where Radio stats lives is #980.

The save reply must echo what was stored

The client renders the device's answer, never its own assumption. Choosing Off does not change the stored mode byte, so a client modelling its own write would show the wrong mode. Clamping has the same shape: the reporting interval is already constrained to 0 through 86400, so the user must see the clamped value, not what they typed. Delivered: the 0xC5 GPS reply carries the stored values after every write.

Power save is hidden where the build cannot drive it

OFFBAND_GPS_POWER_SAVE is per variant and currently only on the QCC badge. The GPS reply's ps_ok byte says whether this radio can run it; without that, the client would offer a mode that does nothing.
